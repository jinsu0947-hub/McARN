# SPEC_Ingest — 데이터 입력부와 좌표계

버전 0.1 · Arnis 포크 · 축척은 실행 파라미터 (기본값 1.75, §2.2)

---

## 0. 원칙

Arnis는 OpenStreetMap을 전제로 만들어져 있다. 이 포크는 **입력부를 국내 공공데이터로 교체한다.**

한국에서 OSM으로 건물을 세우는 것은 있는 데이터를 안 쓰는 것과 같다. 건물통합정보에는 건물마다 층수·용도·사용승인연도가 실측값으로 들어 있고, 표준노드링크에는 도로마다 차로수와 등급이 들어 있다. OSM 한국 데이터에는 대부분 없다.

**교체 범위는 입력부와 좌표계까지다.** 블록 배치, 청크 쓰기, 월드 저장 등 Arnis의 하부 구조는 그대로 쓴다.

| 항목 | 내용 |
|---|---|
| 상류 | `louis-e/arnis` |
| 라이선스 | AGPL-3.0. 공개 시 소스 공개 및 동일 라이선스 유지 |

## 2. 좌표계

### 2.1 관련 좌표계

| 좌표계 | EPSG | 용도 |
|---|---|---|
| WGS84 경위도 | 4326 | 범위 지정, 사용자 입력 |
| GRS80 중부원점 | 5186 | 표준노드링크 |
| GRS80 UTM-K | 5179 | 건물통합정보, 수치표고모델 |

배포본마다 다를 수 있으므로 **파일의 실제 좌표계를 읽어 확인한 뒤 변환한다.** 가정하지 않는다.

내부 처리는 **미터 단위 평면좌표 하나로 통일**한다. EPSG:5186을 기준으로 삼는다.

**전국 단일 원점을 쓴다.** 한국은 서부(EPSG:5185)·중부(5186)·동부(5187) 세 TM 원점이 따로 있지만, 이 프로젝트는 지역마다 원점을 바꾸지 않고 **5186 하나로 고정한다.**

- 전국이 같은 좌표 프레임이면 인접 지역을 나중에 다른 프리셋으로 생성해도 좌표가 이어 붙는다 — 원점이 지역마다 다르면 지역 경계에서 맵을 잇는 것 자체가 별도 변환 작업이 된다
- 국내 최원거리(추자도~독도급)에서도 축척 오차가 0.1% 미만이라 실용적으로 문제가 없다. 서부/동부 원점을 자동 선택하는 로직은 만들지 않기로 결정했다(`PROGRESS.md §7` 참고)
- 프리셋(`SPEC_Scope §5.1` `overrides`)에서 다른 EPSG 코드로 덮어쓰는 것은 허용한다 — 결정은 "기본값을 5186 하나로 고정"이지 "5186만 쓸 수 있다"가 아니다

### 2.2 블록 좌표 변환

```
block_x = round((E - E0) * SCALE)
block_z = round((N0 - N) * SCALE)      // 북쪽이 -Z
block_y2 = round((H - H0) * SCALE * 2) + Y2_BASE
```

| 기호 | 의미 |
|---|---|
| `E, N` | 평면좌표 (m) |
| `H` | 표고 (m) |
| `E0, N0` | 대상 영역 서남단 기준점 |
| `H0` | 대상 영역 최저 표고 |
| `SCALE` | 실행 파라미터. **기본값 1.75** |
| `Y2_BASE` | -88 (= y -44의 반블록 표현) |

`SCALE`을 고정값에서 실행 파라미터로 바꾼 것은 지역 일반화 때문이다 — 다른 지역은 대상 면적·서버 청크 예산이 달라 다른 축척이 필요할 수 있다. 기본값 1.75는 바뀌지 않는다. `SPEC_RoadSection`·`SPEC_StreetFurniture`·`SPEC_BuildingType`·`SPEC_Bridge`의 실측값 표는 전부 **축척을 곱해 반올림하는 공식**으로 다시 쓰였고, 그 문서들의 숫자 표는 `SCALE=1.75`일 때의 산출 예시로 남아 있다. 축척을 바꾸면 그 예시 숫자가 아니라 공식이 적용된다.

**회전은 없다.** 축 정렬을 유지한다.

### 2.3 고도 압축 매핑

**표고에는 `SCALE`을 일정하게 적용하지 않는다.**

봉래산 정상은 약 395 m다. 1.75를 곱하면 691블록이 필요하지만, 지형이
쓸 수 있는 실제 공간은 약 366블록(상한 304, 하한 -62)뿐이다. 등방 축척을
그대로 적용하면 정상부가 잘린다.

수직 축척을 전체적으로 낮추면 경사가 완만해져 주행 감각이 달라진다.
그래서 **낮은 고도는 온전히 두고, 높은 고도만 눌러 담는다.**

| 구간 | 배율 |
|---|---|
| 0 ~ `H_LINEAR` | `SCALE` (온전) |
| `H_LINEAR` 초과 | 점진 감소 |

**`H_LINEAR`는 고정 상수도 프리셋 값도 아니다. scope마다 자동 산출한다.**

```
H_LINEAR = scope 내 도로·건물이 존재하는 지점의 표고 95 퍼센타일
```

- 사람과 차량이 실제로 다니는 고도대(도로·건물이 있는 곳)의 95%가 압축 없이 정확한 축척을 받는다는 뜻이다. 정상부처럼 도로도 건물도 없는 곳만 왜곡된다
- 영도(봉래산 정상 약 395m, 시가지가 대체로 100m 안팎)에서 이 식을 돌리면 `v0.1`이 고정값으로 뒀던 120m 근방이 나온다 — 즉 이전의 "기본 120m"는 이 식이 영도에 대해 내놓는 값을 미리 박아둔 것이었다
- **scope 최고 표고를 축척 그대로(`SCALE`, 압축 없이) 적용해도 세계 높이 상한 안에 들어오면, 압축 자체를 끈다.** 평지가 대부분인 지역은 애초에 눌러 담을 필요가 없다 — `H_LINEAR`를 scope 최고 표고와 같게 두고 압축 계수를 1로 고정하는 것과 같다
- 배율 감소는 연속이어야 한다. 경계에서 급변하면 지형에 단이 생긴다
- 압축이 켜지는 경우, 압축 후 최고 표고가 지형 상한 안에 들어오도록 계수를 scope 최고 표고에서 역산한다

`H_LINEAR`와 압축 계수 산출은 `SPEC_Ingest §6` 계획 단계에서 scope를 한 번 훑어 끝낸다 — 생성 단계가 시작되기 전에 이미 확정된 상수로 쓰인다.

**압축 계수와 `H_LINEAR`는 `manifest.json`에 기록한다.** 이 값이 없으면
블록 높이에서 실제 표고를 되돌릴 수 없다.

### 2.4 도로 폭 예외

**도로 단면에는 `SCALE`을 적용하지 않는다.** 등급별 고정 폭을 쓴다. `SPEC_RoadSection §0` 참조.

위치만 실측을 따르고 단면은 규격화한다. 폭에 축척을 곱하면 매 지점 반올림 오차로 가장자리가 톱니처럼 되고 차선 도색 리듬이 깨진다.

## 3. 도로 입력 — 표준노드링크

출처: 국가교통정보센터(ITS). 노드·링크 셰이프파일.

### 3.1 사용 필드

| 필드 | 용도 |
|---|---|
| `LINK_ID` | 식별자. 버스 노선 경유 링크와 대조 |
| `F_NODE`, `T_NODE` | 그래프 연결 |
| `LANES` | 차로수 |
| `ROAD_RANK` | 도로 등급 |
| `ROAD_NAME` | 표기·확인용 |
| `MAX_SPD` | 보조 판단 |
| 형상 (폴리라인) | 중심선 |

필드명은 배포본에 따라 다를 수 있으므로 실제 파일에서 확인한다.

### 3.2 등급 매핑

`ROAD_RANK` → `SPEC_RoadSection` 등급.

| ROAD_RANK | 구분 | 단면 등급 |
|---|---|---|
| 101, 102 | 고속국도·도시고속 | A |
| 103 | 일반국도 | B |
| 104 | 특별광역시도 | B 또는 C (`LANES` 기준) |
| 105, 106 | 국가지원지방도·지방도 | C |
| 107 | 시군도 | D 또는 E (`LANES` 기준) |
| 108 | 기타 | F |

**`LANES`가 등급을 덮어쓴다.** 등급이 104여도 차로수가 2면 C가 아니라 D로 내린다. 실제 폭은 등급보다 차로수를 따른다.

| LANES | 단면 등급 |
|---|---|
| 6 이상 | A 또는 B |
| 4 | C |
| 2 | D 또는 E |
| 1 또는 결측 | F |

### 3.3 그래프 구성

표준노드링크는 이미 노드-링크 구조다. `SPEC_RoadProfile`의 도로망 그래프와 형태가 같으므로 **세선화 과정이 필요 없다.** 노드와 링크를 그대로 옮기고 종단선형 계산만 적용한다.

후처리 명세에서 P1(마스크 추출)과 P2(중심선 추출)는 폐기한다. P3 이후만 남는다.

## 4. 건물 입력 — 건물통합정보

출처: 국가공간정보포털. GIS건물통합정보 셰이프파일.

라이선스에 비영리 조건이 포함되므로 공개 시 확인이 필요하다.

### 4.1 사용 필드

| 필드 | 용도 |
|---|---|
| 건물 외곽선 (폴리곤) | 형태 |
| 지상 층수 | 높이, 유형, L3 필터 |
| 건물 용도 코드 | 유형 |
| 사용승인일 | 유형 (연대 구간) |
| 구조 코드 | 보조 판단 |
| 건물 식별자 | 결정론적 해시 시드 |

**컬럼명은 배포본마다 다르고, 대개 익명화되어 있다** (예: `A9`=주용도, `A13`=사용승인일처럼 실제 필드를 샘플링해 역추적해야 하는 경우가 흔하다). 이 대응 관계를 코드에 박아넣지 않고 **설정으로 분리**한다 — `SPEC_Scope §5.1`의 `buildings.dbf_schema`가 이름으로 가리키는 매핑 파일이다. 다른 지역 데이터를 처음 넣을 때는 이 매핑이 그 배포본에도 맞는지부터 확인해야 한다 (데이터 검증 리스크이지 코드 구조 문제가 아니다).

**자기 검증은 필수다.** 적재 시점에 다음을 확인하지 않으면 매핑이 어긋나도 조용히 결측이나 엉뚱한 값으로 흘러들어간다.

| 검사 | 내용 |
|---|---|
| 날짜 형태 확인 | 사용승인일로 매핑된 컬럼이 실제로 날짜(또는 연도)로 파싱되는가 |
| 용도 코드집합 대조 | 주용도로 매핑된 컬럼의 값들이 알려진 코드집합 안에 있는가 |

**검증 실패 시 적재를 중단한다.** 경고로 넘기지 않는다 — 매핑 자체가 틀렸다면 이후 모든 건물 속성이 의미 없어지고, `SPEC_Validation §2`의 속성 공백·유형 분포 경고도 원인을 가릴 뿐 근본 문제를 놓친다.

### 4.2 외곽선 처리

1. 좌표 변환 후 블록 격자에 래스터화
2. 도로 점유 영역과 겹치는 부분 오려내기 (`SPEC_RoadSection §5`)
3. 잔여 면적 30% 미만이면 건물 생략
4. 오려낸 외곽선으로 벽 생성

**순서가 중요하다.** 건물을 세운 뒤 깎으면 잘린 단면이 노출된다.

### 4.3 층수·유형

`SPEC_BuildingType §2, §3` 참조. 사용승인일에서 연도만 취해 연대 구간으로 변환한다.

## 5. 지형 입력 — 고도 데이터

### 5.1 소스

**기본값은 Arnis 내장 고도 처리를 그대로 쓴다.**

국토지리정보원 5m 수치표고모델은 정밀하지만 신청·승인 절차가 있어 채택하지 않는다. M0의 목적은 좌표 변환 검증이지 지형 정밀도가 아니다.

| 소스 | 해상도 | 절차 | 상태 |
|---|---|---|---|
| Arnis 내장 | — | 없음 | **기본값** |
| SRTM / Copernicus GLO-30 | 30 m | 없음 | 대체 후보 |
| 브이월드 DEM | 확인 필요 | 오픈API | 대체 후보 |
| 국토지리정보원 5m DEM | 5 m | 신청·승인 | 필요해지면 |

**고도 입력부는 반드시 교체 가능한 모듈로 분리한다.** 나중에 소스만 바꿔 끼울 수 있어야 한다.

### 5.2 처리

1. 대상 영역으로 잘라내기
2. 원본 격자를 블록 격자로 리샘플링 (30 m 격자면 30 × 1.75 = 52.5블록 간격 → 보간 필수)
3. 표고에 `SCALE` 적용 후 반블록 정수화

**보간이 필수다.** 격자 간격이 블록보다 훨씬 크므로 최근접으로 채우면 계단이 생긴다. 쌍선형 보간을 쓴다.

### 5.3 해상도 한계

**30 m급 고도로는 `SPEC_BuildingType §10` 경사지 규칙이 제대로 동작하지 않는다.**

건물 외곽선 내 표고차 `Δ`를 산출해야 하는데, 격자 간격이 건물보다 크면 한 건물이 단일 표고값에 얹힌다. 영도 산복도로 일대 건물이 뭉뚱그려진다.

**M4에서 실제로 문제가 되면 그때 정밀 고도 소스를 도입한다.** 미리 앞당기지 않는다.

### 5.4 수계

| 항목 | 처리 |
|---|---|
| 바다 | 단일 기준 수면. 해안선은 고도 0m 등고선. 조수간만은 무시한다 |
| 하천 | 구간별 평평한 수면 + 단차로 연결한다 (실제 보·낙차공에 대응하는 처리) |
| 수심 | 바닥을 파는 것이 아니라 **수면 높이를 정하고 그 아래를 비운다.** 최소 수심에 못 미치는 지점만 파낸다 |
| 처리 순서 | 생성 단계의 **마지막.** 먼저 채우면 절토·성토가 물을 뚫는다 (`SPEC_Ingest §6` 생성 단계 순서 참고) |
| 축척에 따른 생략 | 폭이 2블록 미만인 하천은 생략하고 지형으로 메운다. 1블록 수로는 표현해도 물로 안 읽힌다 |

**도로가 물을 만나면 절토·성토로 처리하지 않고 교량으로 처리한다** (`SPEC_Bridge` 연동). 도로가 물 위를 그냥 흙으로 메우고 지나가면 하천·해안이 끊긴 것처럼 보인다.

수면을 채우는 순서가 마지막이어야 하는 이유는 `SPEC_BuildingType §10` 절토·성토, `SPEC_RoadProfile P8` 주변 지형 정리 전부 **원지형을 기준으로 계산**하기 때문이다. 수면부터 채우면 그 계산들이 물 위에서 이루어지게 된다.

## 6. 파이프라인

세 단계로 나눈다 — **계획 / 생성 / 기록.** 계획은 블록을 한 개도 쓰지 않고 scope 전체를 한 번 훑어 필요한 값을 전부 확정한다. 생성은 그 계획을 타일 단위로 재생해 블록을 쓴다. 기록은 메타데이터만 남긴다.

이렇게 가른 이유는 **품질 단계(`SPEC_Build` §2)를 올려 재생성할 때** 데이터 재수신과 무거운 계산(노드 높이 전역 해, 95 퍼센타일 산출 등)을 다시 하지 않기 위해서다. 계획은 품질과 무관하게 항상 전부 계산하고 캐시한다 — `terrain` 품질로 한 번 돌리고 `detail` 품질로 다시 뽑아도, 계획 결과가 그대로면 도로 형상이나 건물 판정이 달라지지 않는다.

### 계획 단계 (블록을 쓰지 않음, scope 전체를 한 번 훑음)

```
1. 범위 확정            scope 조각 합집합 → 생성 대상 청크 목록 (SPEC_Scope §1, §2)
2. 데이터 적재           노드링크 / 건물통합정보 / 고도 / (있으면) 노선·정류소 잘라내기
3. 좌표 변환             모두 EPSG:5186 → 블록 좌표
4. H_LINEAR·압축 계수 산출  scope 내 도로·건물 표고 95 퍼센타일 (§2.3)
5. 노드 높이 전역 해      SPEC_RoadProfile P4
6. 구간 종단선형          SPEC_RoadProfile P5 (정수화·재검사까지)
7. 건물 지반고·경사 판정   전면 접도고 → Δ 판정 (SPEC_BuildingType §10.1, §10.2)
8. 유형 결정             용도·연대 → 유형 코드 (SPEC_BuildingType §3)
9. 도로 침범 충돌 판정     외곽선 오려낼 영역 계산 (SPEC_RoadSection §5)
10. 계획 저장            roadgraph.json / buildings.json / stops.json + 사람이 읽을 수 있는 계획 요약
```

5번은 4번보다 뒤, 9번(도로 침범 판정)은 건물 외곽선을 실제로 오려내는 생성 단계보다 앞이어야 한다. 도로 높이가 확정돼야 건물 지반고가 나오고, 침범 영역이 확정돼야 외곽선을 오려낼 수 있다.

`SPEC_Validation §1`의 계획 단계 지표는 여기서 함께 산출된다 — 10번 "계획 저장" 시점에 같이 찍는다.

### 생성 단계 (타일별로 반복)

```
지형 → 도로 → 교량 → 건물 → 파사드 → 가로 요소 → 수계
```

계획에서 이미 확정된 값(노드 높이, 건물 지반고, 유형, 침범 영역)을 그대로 써서 타일별로 블록을 쓴다. 재계산하지 않는다. `SPEC_Build §2`의 `--quality` 단계는 이 안에서만 의미가 있다 — 도로는 품질 단계에 속하지 않고 항상 계획대로 최고 정합성으로 생성된다. 수계는 마지막에 처리한다 (`§5.4`).

### 기록 단계

```
manifest.json + 검증 지표 (validation_report.json, SPEC_Validation)
```

월드 쓰기 자체는 생성 단계 안에서 타일마다 이루어지고, 기록 단계는 그 결과에 대한 메타데이터만 남긴다.

## 7. Arnis 코드와의 관계

| 영역 | 처리 |
|---|---|
| Overpass 질의·OSM 파싱 | 국내 데이터 모듈로 대체 (기존 경로는 옵션으로 보존) |
| 좌표 변환 | 축척·좌표계 반영하여 교체 |
| 도로 생성 | 전면 재작성 (`SPEC_RoadSection`) |
| 건물 생성 | 전면 재작성 (`SPEC_BuildingType`) |
| 지형 생성 | **그대로 사용** (고도 입력부만 교체 가능하도록 분리) |
| 블록 배치·청크 쓰기·월드 저장 | **그대로 사용** |
| GUI | 범위 지정 방식 변경 필요 — 사각형 하나였던 것을 **세 가지 scope 모드(사각형/행정구역 폴리곤/노선 띠) + 축척 입력**으로 바꾼다 (`SPEC_Scope §1`, `§2.2`) |

## 8. 미정

- 버스 노선 데이터 확보 경로 (부산시 공공데이터 vs 국가대중교통정보센터)
- 노선 링크 ID와 표준노드링크 링크 ID의 대조 가능 여부
- 교량 waypoint 실측 확보 — 구조는 프리셋 파일로 확정됐다 (`SPEC_Scope §5.1`, `SPEC_Bridge §0`). 표준노드링크 자체에는 형상 정보가 없으므로 지역마다 사람이 좌표를 찾아 채워야 하는 일은 남는다
- 좌표계 변환 라이브러리 선정 (Rust `proj` 바인딩 여부)
- 셰이프파일 파싱 라이브러리 선정
- 데이터 갱신 주기 대응 — 지금은 1회 스냅샷으로 고정
